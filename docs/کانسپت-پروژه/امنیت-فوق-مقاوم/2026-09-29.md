# BAFT Concept — امنیت فوق‌مقاوم و Privacy-First

**نوع گزارش:** CONCEPT / EXTREME INTERNET SECURITY  
**تاریخ:** 2026-09-29  
**وضعیت:** مفهومی / پژوهشی / آینده پروژه

## اصل بنیادی

هدف نباید «غیرقابل‌هک بودن مطلق» باشد؛ چنین تضمینی از نظر مهندسی قابل‌دفاع نیست.

هدف مناسب‌تر:

> **BAFT Secure Fabric = Compromise-Resistant + Compromise-Contained + Privacy-Preserving + Recoverable**

یعنی سیستم:
- تا حد ممکن نفوذ را سخت کند؛
- اگر نفوذ رخ داد، blast radius را محدود کند؛
- داده دزدیده‌شده را بدون کلید و هویت مجاز بی‌استفاده نگه دارد؛
- نفوذ را سریع کشف کند؛
- هویت/کلید/Session مشکوک را قرنطینه و rotate کند؛
- بعد از compromise بتواند به حالت سالم برگردد.

## مدل امنیتی پیشنهادی

```
User / Workload
      ↓
Strong Identity
      ↓
Continuous Authorization
      ↓
Attested Runtime
      ↓
Encrypted Session
      ↓
Encrypted Data Capsule
      ↓
Distributed / Federated BAFT
```

## 1. Zero Trust واقعی

هیچ اعتماد ضمنی بر اساس:
- IP
- شبکه داخلی
- Region
- مالکیت دستگاه
- اتصال قبلی

وجود نداشته باشد.

هر درخواست باید بر اساس:
- identity
- device/workload state
- policy
- context
- risk
- least privilege

ارزیابی شود.

اصل:

> **Never trust the network location. Trust only cryptographically proven identity + policy.**

## 2. Identity کوتاه‌عمر

Credentialهای طولانی‌عمر خطرناک‌اند.

مدل آینده:
- short-lived workload identity
- automatic rotation
- per-session credential
- scoped capability
- revocation سریع

اگر یک credential دزدیده شود، عمر و دامنه اثر آن محدود باشد.

## 3. Remote Attestation

Node نباید فقط بگوید «من Node معتبرم».

باید بتواند Evidence ارائه کند که:
- software مورد انتظار را اجرا می‌کند؛
- configuration مجاز دارد؛
- boot/runtime state قابل قبول است.

Attestation نباید به‌تنهایی اعتماد ایجاد کند؛ فقط یک input برای policy باشد.

## 4. Data Capsule

کانسپت مهم:

هر قطعه داده حساس به‌جای «فایل ساده» یک Capsule باشد:

```
Ciphertext
+ Integrity Tag
+ Data Identity
+ Policy Reference
+ Key Reference
+ Expiry
+ Provenance
```

اصل:

> **داده باید خودش محافظت‌شده باشد، نه فقط دیسکی که روی آن قرار گرفته است.**

اگر storage، database یا relay compromise شد، مهاجم ciphertext بگیرد؛ نه plaintext.

## 5. Key Release فقط به Workload مجاز

کلید داده فقط زمانی آزاد شود که هم‌زمان:
- identity معتبر باشد؛
- policy اجازه دهد؛
- runtime attestation قابل قبول باشد؛
- Session معتبر باشد؛
- context/risk از threshold عبور نکند.

در نتیجه سرقت ciphertext به‌تنهایی مفید نباشد.

## 6. Cryptographic Erasure

برای داده‌های حساس، حذف key باید به معنی غیرقابل‌بازیابی‌شدن عملی داده باشد.

این مدل می‌تواند برای:
- retention expiry
- revocation
- user delete
- incident response

استفاده شود.

## 7. Forward Secrecy

Compromise کلید فعلی نباید به مهاجم اجازه دهد Sessionهای قدیمی را decrypt کند.

کلیدهای Session باید:
- ephemeral
- regularly rotated
- independent

باشند.

## 8. Post-Compromise Security

هدف بلندپروازانه‌تر:

اگر یک endpoint در زمان T compromise شد ولی بعد پاک‌سازی و key rotation انجام شد، compromise قبلی نباید دسترسی نامحدود آینده بدهد.

مفهوم ratcheting و epoch rotation می‌تواند از پروتکل‌هایی مثل MLS الهام بگیرد، ولی باید برای threat model خود BAFT طراحی و اثبات شود.

## 9. Post-Quantum Agility

BAFT نباید crypto اختصاصی اختراع کند.

معماری باید بتواند الگوریتم‌ها را بدون بازطراحی کل سیستم تعویض کند.

جهت استاندارد:
- ML-KEM برای key establishment
- ML-DSA / SLH-DSA برای signature use cases
- hybrid TLS key agreement

Crypto agility از «انتخاب الگوریتم قوی» مهم‌تر است؛ چون الگوریتم‌ها و threatها در طول عمر شبکه تغییر می‌کنند.

## 10. Security Compartmentalization

هیچ component نباید کل قدرت سیستم را داشته باشد.

مثلاً:
- BCC نباید payload plaintext داشته باشد.
- Relay نباید signing key داشته باشد.
- Telemetry backend نباید data key داشته باشد.
- Node compromise نباید trust root را افشا کند.
- یک Region نباید کل Federation را compromise کند.

اصل:

> **No single compromise should reveal everything.**

## 11. Split Trust

برای عملیات بسیار حساس می‌توان اعتماد را میان چند authority تقسیم کرد.

مثلاً:
- Key release نیازمند 2-of-3 policy authorities
- Recovery witnessها مستقل باشند
- high-risk configuration change نیازمند چند approval باشد

این مدل باید فقط برای operationهای حساس باشد، نه data plane روزمره.

## 12. Capability-Based Access

به‌جای accountهایی با permission وسیع، token/capability محدود صادر شود:

- فقط یک سرویس
- فقط یک عملیات
- فقط یک Session
- فقط چند دقیقه
- بدون امکان delegation مگر صریح

سرقت یک capability کوچک نباید دسترسی عمومی ایجاد کند.

## 13. Data Minimization

بهترین داده برای محافظت:

> داده‌ای است که اصلاً جمع نشده.

Telemetry باید:
- حداقلی
- purpose-bound
- retention-bounded
- aggregated در صورت امکان
- جدا از هویت شخصی

باشد.

## 14. Privacy-Preserving Identity

همه سرویس‌ها لازم نیست identity جهانی و دائمی یک کاربر را ببینند.

می‌توان از identityهای:
- service-specific
- rotating
- pseudonymous
- unlinkable where possible

استفاده کرد.

هدف:

> **Authentication بدون ساختن یک شناسه جهانی برای ردیابی فرد.**

## 15. Metadata Privacy

E2EE به‌تنهایی metadata را پنهان نمی‌کند.

BAFT باید صریحاً بررسی کند:
- چه کسی با چه کسی ارتباط دارد؟
- چه زمانی؟
- چه مدت؟
- چه حجم؟
- کدام سرویس؟

استانداردهایی مثل TLS ECH بخشی از metadata handshake مانند SNI را محافظت می‌کنند.

BAFT باید از privacy استاندارد استفاده کند، نه تکنیک‌های اختصاصی برای «نامرئی‌شدن».

## 16. مرز مهم: Privacy ≠ IDS Evasion

هدف نباید این باشد که BAFT از ابزار امنیتی مجاز مالک شبکه «غیرقابل‌تشخیص» باشد.

معماری درست:

- برای ناظر غیرمجاز: حداقل metadata و payload رمز‌شده
- برای مالک مجاز سیستم: audit، health، anomaly و policy visibility
- بدون افشای payload مگر ضرورت مشخص و مجاز

یعنی:

> **Private from unauthorized observers, observable to authorized defenders.**

## 17. Intrusion Detection

تشخیص نفوذ باید چندلایه باشد:

- identity anomaly
- impossible travel / impossible workload state
- unusual Session creation
- abnormal data volume
- policy violation
- unexpected binary/config
- attestation failure
- key-use anomaly
- lateral movement pattern
- unusual control-plane action

AI می‌تواند anomaly را پیشنهاد دهد، ولی block/revoke نهایی باید با policy deterministic محدود شود.

## 18. BAFT Breach Mode

اگر compromise محتمل شد:

```
Detect
→ Isolate
→ Freeze privilege escalation
→ Revoke identity
→ Rotate keys
→ Quarantine Session
→ Preserve evidence
→ Re-attest
→ Rebuild trust
→ Controlled rejoin
```

هدف این نیست که همه چیز shutdown شود.

هدف:
**blast radius کوچک + recovery سریع**

## 19. Canary / Honeytoken دفاعی

داده یا credentialهای جعلی و بدون ارزش عملی می‌توانند فقط برای detection استفاده شوند.

اگر کسی آن‌ها را touch/use کرد:
- intrusion signal
- session isolation
- forensic event

این باید دفاعی و داخلی باشد.

## 20. Software Supply Chain

Crypto قوی روی binary آلوده بی‌فایده است.

نیاز:
- signed commits/releases
- reproducible builds در حد امکان
- SBOM
- dependency pinning
- provenance
- isolated builders
- artifact signing
- vulnerability scanning
- rapid patch process

## 21. Memory Safety

Network-facing code و crypto-adjacent code باید تا حد ممکن در memory-safe language باشد.

Go در این زمینه مزیت معماری BAFT است، ولی:
- unsafe
- cgo
- native libraries
- parser boundaries

باید audit شوند.

## 22. Formal Methods

بخش‌هایی که ارزش formal verification یا model checking دارند:

- ECRL authority
- replay/frontier invariants
- key state transitions
- revocation
- capability delegation
- recovery
- distributed trust state

همه code نیازمند formal verification نیست؛ فقط هسته‌هایی که failure آن‌ها فاجعه‌آمیز است.

## 23. Secure-by-Default

نسخه production نباید با:
- default password
- disabled TLS
- permissive ACL
- wildcard trust
- shared admin key
- debug endpoint باز

قابل راه‌اندازی باشد.

اگر secure setup سخت است، product design باید آن را ساده کند؛ نه اینکه security را optional کند.

## 24. Secret Isolation

Secretها در config file ساده نگهداری نشوند.

در deployment حساس:
- HSM
- TPM
- secure enclave / isolated key service
- OS keyring

به‌کار رود.

ولی hardware trust نیز باید attested و revocable باشد.

## 25. Least Data at Rest

اگر BAFT فقط transit است، payload نباید بی‌دلیل ذخیره شود.

اصل:
- no payload logging by default
- metadata minimization
- bounded diagnostic retention
- sensitive crash dump protection

## 26. Security Domains

هر سازمان/Region/tenant یک blast radius جدا داشته باشد.

Compromise یک Tenant:
- نباید Tenant دیگر را افشا کند.

Compromise Region A:
- نباید Trust Root کل Fabric را بدهد.

## 27. Recovery after Compromise

Backup ساده کافی نیست.

Backup آلوده می‌تواند malware/config compromise را برگرداند.

Recovery باید:
- trusted baseline
- signed configuration
- known-good artifact
- key rotation
- identity reissue
- attestation
- staged rejoin

داشته باشد.

## 28. Privacy Audit

علاوه بر security audit، BAFT باید Privacy Audit جدا داشته باشد:

- چه metadataای جمع می‌شود؟
- چه کسی می‌بیند؟
- چقدر نگه می‌داریم؟
- آیا cross-service linkable است؟
- آیا حذف واقعی ممکن است؟
- آیا aggregate کافی است؟

## 29. Security Invariants پیشنهادی

```
No implicit network trust
No plaintext sensitive payload at rest by default
No long-lived universal credential
No single component owns all secrets
No stale identity after revocation
No unverified software in trusted path
No silent downgrade
No unaudited privilege escalation
No payload exposure to control plane
No indefinite post-compromise access
```

## 30. چیزی که نمی‌توانیم تضمین کنیم

BAFT نباید ادعا کند:

- 100% unhackable
- impossible to exploit
- impossible to detect
- impossible to compromise
- impossible to misuse

ادعای حرفه‌ای:

> **Designed to reduce compromise probability, limit compromise impact, protect data even after infrastructure breach, and recover trust after intrusion.**

## 31. محصول مفهومی

### BAFT Shield
Zero Trust + identity + policy + isolation.

### BAFT Vault
Data Capsule + key isolation + crypto erasure.

### BAFT Sentinel
Attestation + intrusion/anomaly detection + breach response.

### BAFT Privacy Plane
metadata minimization، rotating identity و privacy audit.

### BAFT Trust Federation
trust-domain federation بدون trust root واحد جهانی.

## North Star

> **BAFT Security should not depend on nobody ever getting in.**

بلکه:

> **Even if one layer is compromised, identity, keys, data, sessions and other trust domains should remain protected as far as technically possible; the breach should be detectable, containable and recoverable.**

بهترین تعریف:

# BAFT Extreme Security = Assume Breach, Minimize Trust, Encrypt the Data, Isolate the Keys, Contain the Damage, Recover the Trust.
