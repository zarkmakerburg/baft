# BAFT — کاربرد جهانی و ارزیابی سود/زیان

**نوع گزارش:** CONCEPT / FUTURE IMPACT  
**تاریخ:** 2026-09-29  
**وضعیت:** مفهومی / پژوهشی

## تعریف پیشنهادی

> **BAFT = Internet Session Continuity Layer**

هدف: جداکردن state منطقی Session از Carrier و Path فیزیکی.

## مسئله جهانی

در بسیاری از سیستم‌ها تغییر شبکه، failover دیتاسنتر، تغییر ISP، maintenance gateway یا شکست Carrier باعث reconnect و rebuild شدن state application می‌شود.

BAFT می‌تواند بررسی کند آیا می‌شود:

> Carrier شکست بخورد، اما Session منطقی تا حد امکان زنده بماند.

## کاربردهای بالقوه

### Multi-cloud / Multi-region
حفظ stateful connection هنگام failover بین regionها.

### Enterprise Multi-ISP
شعب، فروشگاه‌ها، کارخانه‌ها و edge siteهایی که چند uplink دارند.

### Edge Computing
استفاده به‌عنوان continuity sidecar بدون الزام تغییر Application.

### Service-to-Service
جداکردن service identity از IP و Node.

### Satellite / Maritime / Aviation
کمک به path instability و تغییر uplink؛ نه جایگزین DTN برای قطع طولانی.

### Disaster / Emergency Networks
جابجایی میان fiber، microwave، cellular و satellite در صورت وجود path end-to-end.

### Industrial Gateways
افزایش resilience ارتباطی، با این محدودیت که byte continuity جای safety semantics را نمی‌گیرد.

### IoT Gateways
برای gatewayها مناسب‌تر از tiny sensorها، به‌خاطر هزینه state و replay memory.

## جاهایی که BAFT احتمالاً مزیت کمی دارد

- HTTP کوتاه و معمولی
- شبکه‌های کاملاً disconnected برای مدت طولانی
- tiny IoT
- consumer VPN در صورتی که فقط Tunnel دیگری باشد
- database transaction exactly-once؛ چون byte continuity مساوی transaction semantics نیست

## ریسک‌های اصلی

### Complexity
خطر silent duplicate یا silent loss از disconnect واضح بدتر است.

### State Cost
Replay buffer، tombstone، timer و session state در scale بالا هزینه جدی دارند.

### Resource Attack
مهاجم می‌تواند Session باز کند و state نگه دارد؛ resource accounting بخشی از security است.

### Privacy
Control plane نباید telemetry را به metadata surveillance تبدیل کند.

اصل مناسب:

> Observe state, not content.

### Centralization Risk
BCC نباید باعث شود control-plane outage مساوی data-plane outage شود.

### Deployment Friction
اگر هر endpoint، application و شبکه نیازمند تغییر باشد adoption سخت می‌شود؛ sidecar/gateway deployment مطلوب‌تر است.

## شرط ادامه پروژه

BAFT باید experimentally بتواند نشان دهد:

```
carrier failure
without application failure
```

همراه با:

- 0 missing bytes
- 0 duplicate bytes
- bounded memory
- bounded recovery time
- no stale authority

اگر این هدف قابل‌اثبات نباشد، مزیت اصلی پروژه از بین می‌رود.

## Stop Condition

اگر نسخه بالغ BAFT نتواند در workload واقعی نسبت به:

- reconnect معمولی
- QUIC migration
- MPTCP / Multipath QUIC
- application-level recovery

مزیت measurable نشان دهد، باید architecture pivot یا حتی پروژه متوقف شود.
