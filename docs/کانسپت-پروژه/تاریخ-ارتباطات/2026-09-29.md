# BAFT Concept — درس‌های فراموش‌شده از ارتباطات باستانی و تاریخی

**نوع گزارش:** CONCEPT / HISTORICAL COMMUNICATION SYSTEMS  
**تاریخ:** 2026-09-29  
**وضعیت:** مفهومی / پژوهشی / آینده پروژه

## فرضیه مرکزی

بخش مهمی از تاریخ ارتباطات نشان می‌دهد که افزایش کارایی همیشه با «قوی‌ترکردن فرستنده» به دست نیامده است.

بسیاری از شبکه‌های موفق تاریخی بر چند اصل ساده تکیه می‌کردند:

- مسیر به ایستگاه‌های کوتاه و آماده تقسیم شود؛
- حامل عوض شود ولی پیام عوض نشود؛
- ایستگاه بعدی از قبل آماده باشد؛
- پیام‌های کنترلی کوتاه و دارای واژگان محدود باشند؛
- برای پیام مهم، handoff و acknowledgement صریح وجود داشته باشد؛
- در قطع مسیر، داده نگه داشته و بعداً منتقل شود؛
- authorization مسیر و استفاده از شبکه جدا از خود پیام باشد.

این اصول می‌توانند برای BAFT به زبان مدرن بازطراحی شوند.

---

# 1. شبکه چاپار هخامنشی — Carrier عوض می‌شود، پیام ادامه دارد

راه شاهی هخامنشی دارای ایستگاه‌های منظم بود و پیام از یک سوار به سوار بعدی منتقل می‌شد. اصل مهم این سیستم این نبود که یک اسب تمام مسیر را سریع‌تر بدود؛ بلکه این بود که **حامل خسته کنار برود و حامل آماده بعدی فوراً ادامه دهد**.

ترجمه معماری برای BAFT:

> **Carrier should be replaceable without changing Logical Session identity.**

کانسپت پیشنهادی:

## BAFT Chapar

هر مسیر دارای مجموعه‌ای از Carrier/Relay آماده باشد:

- Active
- Warm
- Standby
- Failed

در failure، recovery از صفر شروع نشود؛ همان‌طور که چاپار بعدی منتظر رسیدن پیام بود، Carrier بعدی از قبل authenticated و health-checked باشد.

---

# 2. چاسکی‌های اینکا — کوتاه‌کردن hop به جای قوی‌کردن endpoint

شبکه اینکا پیام‌رسان‌هایی داشت که در ایستگاه‌های ۱۰ تا ۱۵ کیلومتری پیام و کِیپو را به نفر بعدی تحویل می‌دادند.

اصل:

> یک مسیر بلند را به بخش‌های کوتاه، قابل‌کنترل و محلی تقسیم کن.

برای BAFT:

- local path repair
- regional relays
- short failure domains
- regional health decisions

می‌تواند بهتر از یک connection عظیم و شکننده‌ی end-to-end باشد.

کانسپت:

## BAFT Chaski Path

یک Session ممکن است روی چند Segment حرکت کند، در حالی که هر Segment failure domain مستقل دارد.

---

# 3. «باتون» یا Baton — Authority باید صریح منتقل شود

در relay واقعی، پیام در هر لحظه دست یک حامل است.

برای BAFT همین مفهوم می‌تواند به‌صورت formal استفاده شود:

## Epoch Baton

در هر لحظه فقط یک Carrier/Owner حق mutation authoritative داشته باشد.

انتقال باید:

```
Old Owner
→ Prepare
→ Proof
→ Handoff
→ New Owner
→ Old Owner fenced
```

باشد.

این استعاره با ECRL هم‌راستا است:

> Carrier قابل تعویض است، Authority نه؛ Authority باید انتقال پیدا کند.

---

# 4. Polybius — Attention Handshake قبل از Payload

Polybius برای سیستم مشعل خود توضیح می‌دهد که فرستنده ابتدا دو مشعل بالا می‌برد و منتظر پاسخ مشابه گیرنده می‌ماند؛ سپس ارسال پیام شروع می‌شود.

این تقریباً یک primitive تاریخی از:

```
Are you ready?
Yes, I am ready.
Now send.
```

است.

برای BAFT درس مهم:

## Ready باید یک state واقعی باشد، نه فرض زمانی.

قبل از ارسال state حساس یا replay:

- طرف مقابل حاضر باشد؛
- generation درست باشد؛
- authority روشن باشد؛
- readiness صریح اثبات شده باشد.

این اصل مستقیماً برای recovery protocol اهمیت دارد.

---

# 5. Polybius Grid — واژگان کوچک برای Control Plane

Polybius حروف را در یک ماتریس ۵×۵ قرار می‌داد و با دو مختصات آن‌ها را ارسال می‌کرد.

اصل مدرن:

> Control Plane نباید متن آزاد و پرحجم حمل کند اگر یک vocabulary محدود کافی است.

BAFT می‌تواند برای Control Plane از codeهای کوچک و نسخه‌دار استفاده کند:

- READY
- COMMIT
- ACK
- STALE
- REVOKED
- REPLAY_REQUIRED
- DRAIN
- DEGRADED
- REJOIN

به‌جای پیام‌های آزاد با semantics مبهم.

---

# 6. تلگراف نوری Chappe — Control Plane بسیار سریع و کوچک

شبکه Chappe پیام را با مجموعه‌ای از signalهای ازپیش‌تعریف‌شده میان برج‌های relay منتقل می‌کرد. سیستم تاریخی دارای vocabulary مشخص و relayهای line-of-sight بود.

درس BAFT:

## Control traffic و Data traffic یک چیز نیستند.

ممکن است Control Plane:
- بسیار کوچک
- سریع
- دارای priority بالا
- روی path مستقل

باشد، در حالی که Payload روی Carrier دیگری حرکت کند.

کانسپت:

## BAFT Beacon Plane

یک مسیر بسیار کم‌حجم برای:

- health
- authority
- path failure
- epoch
- emergency reconfiguration

که حتی در congestion شدید data plane بتواند کار کند.

Beacon نباید payload کاربر را حمل کند.

---

# 7. Talking Drums و Whistled Languages — استفاده از Context مشترک

برخی زبان‌های سوتی و طبل‌های سخنگو مقدار زیادی معنا را با یک کانال فیزیکی بسیار محدود منتقل می‌کنند، چون sender و receiver یک زبان و context مشترک دارند.

درس مناسب برای BAFT:

> Shared context can reduce control overhead.

نه اینکه payload کاربر را با روش مبهم فشرده کنیم.

مثلاً دو Node که قبلاً بر:
- SessionID
- Epoch
- PlanDigest
- RouteID
- Capability Set

توافق کرده‌اند، در recovery لازم نیست همه state را هر بار دوباره ارسال کنند؛ در مواردی که correctness اجازه می‌دهد می‌توان به digest/referenceهای کوچک تکیه کرد.

کانسپت:

## BAFT Codex

یک واژگان protocol کوچک، versioned و cryptographically bound برای control state.

---

# 8. کِیپو — داده ساختاریافته جدا از حامل

چاسکی فقط پیام شفاهی حمل نمی‌کرد؛ کِیپو نیز به‌عنوان record ساختاریافته جابه‌جا می‌شد.

درس:

> Message state باید از Carrier state مستقل باشد.

برای BAFT:

- Carrier = وسیله انتقال
- Session State = داده منطقی
- Proof/Digest = record انتقال‌پذیر

این جداسازی برای آینده‌ی durable recovery مهم است.

---

# 9. Roman Cursus Publicus — شبکه برای همه باز نبود

سامانه پست رسمی روم دارای ایستگاه‌های تعویض وسیله و استراحت بود و استفاده از آن برای مأموریت‌های مجاز حکومتی کنترل می‌شد.

درس امنیتی:

## Reachability ≠ Authorization

داشتن دسترسی فیزیکی به شبکه نباید به معنی اجازه استفاده از همه Routeها باشد.

برای BAFT:

- Node Identity
- Network Admission
- Route Capability
- Resource Quota

باید از هم جدا باشند.

این همان جهتی است که BAFT در peer allowlist و route allowlist دنبال می‌کند.

---

# 10. Heliograph — Carrier باید با محیط انتخاب شود

Heliograph با نور خورشید و آینه پیام می‌فرستاد: بسیار ساده و کم‌انرژی، ولی کاملاً وابسته به شرایط دید و نور.

درس:

> هیچ Carrierی در همه شرایط بهترین نیست.

BAFT نباید به یک Transport برای تمام محیط‌ها وابسته شود.

Path Broker آینده می‌تواند بر اساس:

- latency
- loss
- availability
- energy
- cost
- environment

Carrier را انتخاب کند.

---

# 11. Relay Regeneration — هر hop خطا را ادامه ندهد

تلگراف‌های بعدی از relay برای دریافت signal ضعیف و بازتولید signal قوی استفاده کردند.

درس مدرن:

> هر Segment نباید corruption و uncertainty بخش قبلی را کورکورانه ادامه دهد.

در BAFT Relay/Federation آینده هر hop می‌تواند:
- authenticate
- validate frame/state
- enforce quota
- reject invalid transition

کند.

اما end-to-end identity و payload confidentiality باید حفظ شود.

---

# 12. شبکه صوتی/سوتی — کانال narrow ولی semantics غنی

زبان‌های سوتی در محیط کوهستانی برای ارتباط دوربرد استفاده شده‌اند و از ویژگی‌های ضروری زبان برای انتقال معنا روی کانال بسیار محدود استفاده می‌کنند.

درس برای BAFT Mesh/Island:

در شرایط بسیار degraded شاید لازم نباشد full service برقرار باشد.

می‌توان یک:

## Minimal Survival Protocol

داشت که فقط اطلاعات حیاتی را نگه دارد:

- node alive
- gateway available
- emergency message
- trust update
- route health
- rejoin request

یعنی:

> در degradation، semantics را کوچک کن؛ شبکه را خاموش نکن.

---

# 13. Direct Physical Channel — اصل «Direct First»

نمونه‌های تاریخی ارتباط آکوستیکی/مکانیکی مستقیم نشان می‌دهند اگر دو endpoint بتوانند مستقیماً با کیفیت مناسب ارتباط بگیرند، واسطه همیشه ارزشمند نیست.

برای BAFT:

```
Direct path good?
→ use Direct
```

و فقط وقتی لازم است:
- Relay
- Edge
- Multi-hop
- Recovery path

وارد شود.

این اصل برای Gaming، EV، Crypto و BAFT Federation مشترک است.

# 14. مهم‌ترین الگوهای قابل استفاده

## A. Pre-positioned Replacement
از چاپار و چاسکی:

> replacement قبل از failure آماده باشد.

کاربرد:
Warm Carrier Pool.

## B. Local Handoff
از relay station:

> هر hop فقط مسئول handoff درست به hop بعدی باشد.

کاربرد:
Regional BAFT.

## C. Explicit Readiness
از Polybius:

> قبل از Payload، حضور و آمادگی receiver اثبات شود.

کاربرد:
Recovery Barrier.

## D. Small Control Vocabulary
از Polybius و Chappe:

> Control semantics محدود، versioned و دقیق باشد.

کاربرد:
BAFT Beacon / Codex.

## E. Structured State Independent of Carrier
از کِیپو:

> state منطقی را از وسیله حمل جدا کن.

کاربرد:
Continuity Certificate / Durable ECRL.

## F. Store-and-Forward
از courier networks:

> نبود اتصال هم‌زمان الزاماً به معنی از دست رفتن پیام نیست.

کاربرد:
BAFT Ferry / Island Mode.

## G. Environment-Adaptive Medium
از heliograph:

> Carrier مناسب تابع محیط است.

کاربرد:
Path Broker.

## H. Authorization to Use Infrastructure
از cursus publicus:

> network access با service authorization یکی نیست.

کاربرد:
Capability-Based Routing.

# 16. ایده جدید: Two-Speed Internet

شبکه‌های تاریخی اغلب عملاً دو سرعت داشتند:

- signal سریع و کوتاه
- payload/نامه/کالا کندتر

BAFT می‌تواند همین تفکیک را مدرن کند:

## Fast Plane
- health
- epoch
- authority
- route state
- emergency control

## Bulk Plane
- user data
- large synchronization
- backup
- content

در congestion یا outage:

Fast Plane باید زنده‌تر از Bulk Plane بماند.

---

# 17. ایده جدید: Station Locality

شبکه‌های تاریخی موفق به مرکز اجازه نمی‌دادند درباره هر قدم کوچک تصمیم بگیرد.

ایستگاه محلی:
- اسب را عوض می‌کرد؛
- پیام را تحویل می‌گرفت؛
- بعدی را راه می‌انداخت.

برای BAFT:

Regional Controller باید بتواند local failover انجام دهد بدون round-trip به Global BCC.

اصل:

> **Global policy, local execution.**

---

# 18. ایده جدید: Continuity Receipt Chain

هر handoff می‌تواند receipt کوچک و tamper-evident ایجاد کند:

```
Carrier A
→ receipt
Carrier B
→ receipt
Carrier C
```

نه برای logging payload؛ فقط:

- SessionID
- Epoch
- Previous Owner
- New Owner
- Frontier Digest
- timestamp/sequence
- signatures

این ایده به Continuity Certificate نزدیک است.

# 19. چه چیزهایی را نباید از گذشته کپی کنیم؟

شبکه‌های تاریخی محدودیت‌های جدی داشتند:

- confidentiality کم یا صفر
- اعتماد زیاد به courier/operator
- route ثابت
- ظرفیت بسیار پایین
- امکان interception
- centralized authority
- lack of cryptographic integrity
- weather dependence
- manual error

پس هدف:

> **Copy the architectural principle, not the historical security model.**

# 20. آزمایش‌های پژوهشی پیشنهادی

## H1 — Warm Station Handoff
مقایسه:
- cold carrier recovery
- pre-authenticated warm carrier

معیار:
- recovery p50/p95/p99
- CPU/memory cost

## H2 — Beacon Plane
Control Plane بسیار کوچک تحت congestion شدید.

معیار:
- time-to-failure-detection
- control delivery rate
- payload independence

## H3 — Codex Compression
مقایسه full recovery state با digest/reference-based control.

شرط:
- zero loss of correctness
- explicit mismatch fallback

## H4 — Regional Local Repair
قطع Control Plane مرکزی و بررسی local recovery.

## H5 — Energy-Aware Carrier
انتخاب مسیر بر اساس latency + energy + cost.

## H6 — Store-and-Rejoin
Island Mode، queue bounded و safe rejoin.

# جمع‌بندی

مهم‌ترین درس تاریخ ارتباطات برای BAFT شاید این باشد:

> **شبکه سریع و مقاوم الزاماً شبکه‌ای نیست که یک لینک فوق‌العاده داشته باشد؛ شبکه‌ای است که بتواند پیام را بدون از دست دادن هویت و معنا، سریع و درست از یک حامل سالم به حامل بعدی تحویل دهد.**

به زبان BAFT:

```
Keep the message.
Replace the carrier.
Prepare the next station.
Keep control signals small.
Prove every handoff.
Survive temporary disconnection.
```

این فلسفه از چاپار هخامنشی تا چاسکی اینکا، Polybius، Chappe و relay telegraph بارها در شکل‌های مختلف دیده می‌شود.

اگر BAFT بتواند این اصول قدیمی را با:
- cryptographic identity
- bounded memory
- formal invariants
- modern transports
- distributed control

ترکیب کند، بخشی از «نوآوری» آن شاید نه از اختراع همه‌چیز از صفر، بلکه از **بازکشف اصول بسیار قدیمی و پیاده‌سازی دقیق آن‌ها برای اینترنت جدید** بیاید.
