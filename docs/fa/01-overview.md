# 01 — معرفی، هدف و مرز پروژه

## تعریف کوتاه

BAFT یک relay امن، احرازشده و محدودشده برای TCP است که میان دو Node تحت کنترل اپراتور کار می‌کند. هدف طراحی، ساخت یک data plane قابل‌آزمون با امنیت سخت‌گیرانه، backpressure واقعی، state صریح و مسیر توسعه مرحله‌ای است.

## سناریوی پایه

- IR نقش `dialer` دارد.
- EX نقش `listener` دارد.
- IR روی یک آدرس محلی مانند `127.0.0.1:1443` اتصال می‌پذیرد.
- آن اتصال به یک Flow BAFT تبدیل می‌شود.
- Flow از یک Shard عبور می‌کند.
- EX فقط یک Route ازپیش‌تعریف‌شده مانند `service-main` را resolve می‌کند.
- EX به مقصد ثابت همان Route مانند `127.0.0.1:2443` متصل می‌شود.
- بایت‌ها در هر دو جهت منتقل می‌شوند.

## اصل «Route به‌جای مقصد دلخواه»

BAFT عمداً چیزی شبیه `OPEN host=... port=...` ندارد. peer فقط یک شناسه Route می‌فرستد. نگاشت واقعی Route در Node مقصد تعریف می‌شود. این تصمیم سه هدف دارد:

1. peer نتواند BAFT را به proxy مقصد-دلخواه تبدیل کند؛
2. authorization مستقل از transport و CA بماند؛
3. audit و تست امنیتی روی مجموعه مقصدهای محدود ممکن باشد.

## هدف‌های فنی

- امنیت transport با TLS 1.3 و mTLS؛
- هویت Node بر پایه گواهی تأییدشده؛
- parser باینری محدود و قابل fuzz؛
- Flow دوطرفه با half-close؛
- کنترل جریان صریح با ACK و WINDOW؛
- memory budget سراسری و backpressure؛
- چند Flow و چند Shard بدون صف نامحدود؛
- resume دقیق در مراحل بعد، بدون ادعای resume بعد از restart Process؛
- benchmark و پژوهش قابل‌بازتولید و بدون ساختن نتیجه.

## عدم‌هدف‌ها

BAFT قرار نیست:

- یک VPN عمومی یا سرویس arbitrary proxy باشد؛
- تنظیمات Xray یا سرویس مقصد را خودکار تغییر دهد؛
- از CA trust به‌تنهایی نتیجه authorization بگیرد؛
- با خاموش‌کردن verification یا plaintext fallback «دسترس‌پذیری» ایجاد کند؛
- تضمین سرعت ثابت روی اینترنت عمومی بدهد؛
- ادعای تشخیص‌ناپذیری همگانی داشته باشد؛
- payload کاربران را برای analytics یا debugging ذخیره کند.

## وضعیت کنونی در برابر طراحی نهایی

مرحله B عملاً vertical slice امن را ساخته است. Stage C در حال تثبیت allocator، DRR، صف کنترل و رفتار receiver کند است. Resume، epoch، replay بین Carrierهای جایگزین و tombstone متعلق به Stage D هستند و هنوز قابلیت جاری محسوب نمی‌شوند.

## چرا پروژه مرحله‌ای است؟

ترتیب مراحل برای جلوگیری از این طراحی شده که performance یا قابلیت‌های آزمایشی قبل از correctness و security وارد مسیر اصلی شوند. هر Stage خروجی و gate دارد؛ عبور از Stage فقط با شواهد تست انجام می‌شود، نه با وجود کد یا TODO.
