# گزارش هماهنگی هوشا — R3.1 / Morphing

تاریخ: ۲۸ سپتامبر ۲۰۲۶، تهران. مبنا: شاخه R3 در commit `a4d45e5`.
وضعیت تحویل: **نامزد بررسی v0.2.0-pro-rc1**؛ انتشار نهایی v0.2-Pro تأیید نشده است.

## الف) تحلیل فنی

قراردادهای STATUS/PLAN، Stage D در سند 15D، Reachability R1/R2، TWRL، PADL، پروتکل و ADRها با تغییرات تطبیق داده شدند. سند Stage D شماره 20 طبق متن خودش منسوخ است. Stage D ادامه داده نشده و recovery.enabled همچنان false است.

لایهٔ recordshape از bucket قطعی به نمونه‌گیری CDF نرمال یا لاپلاسِ محدودشده تغییر کرد. منبع تصادف crypto/rand است؛ padding تا سقف بایت و نسبت سربار کنترل می‌شود. طول‌ها به توان دو گرد نمی‌شوند و مقادیر خارج از دامنه به یک طول انتهایی clamp نمی‌شوند. پارامترهای میانگین و انحراف معیار مربوط به توزیع پایه‌اند؛ محدودسازی، میانگین مشاهده‌شده را تغییر می‌دهد.

ترتیب مسیر: دادهٔ Session، رمزنگاری Noise، envelope احتمالی، بدنهٔ HTTP/2، سپس TLS/TCP. شمارنده‌های Noise، offset داده، credit، رینگ TWRL و frontier بازیابی دست‌کاری نمی‌شوند. خطای نوشتن یا احراز هویت، اتصال را غیرقابل‌استفاده می‌کند تا تلاش مجدد با nonce ناهماهنگ رخ ندهد.

اثر قابل دفاع: حذف امضای **طول‌های ثابت رکورد کاربردی**. Gaussian padding به‌تنهایی تطابق با HTTPS واقعی یا شکست فیلترینگ آماری ایران را ثابت نمی‌کند؛ مرز write با مرز بستهٔ TLS/TCP یکی نیست. این پیاده‌سازی ادعای اختراع بی‌سابقه ندارد.

مسیر Runtime نیز به Noise متصل شد. حالت صریح noise از TLS معتبر سمت سرور و کلیدهای Noise pin‌شدهٔ دوطرف استفاده می‌کند. حالت قبلی mTLS در نبود این تنظیم فعال می‌ماند. هویت از کلید pin‌شده می‌آید، نه HELLO. allowlist مسیر و لغو هویت برقرار است؛ لغو serial/fingerprint گواهی کلاینت مختص mTLS است.

در حالت Noise، درخواست وب عادی، پیام IK خراب و کلید ناشناس به همان HTML می‌رسند. پیش از احراز هویت پیام اول، پاسخ موفق تونل ارسال نمی‌شود. تعداد handshake معلق و مهلت‌ها محدودند. پاسخ HTML روی TLS نامعتبر امکان‌پذیر نیست و اثرانگشت گواهی، TLS و رفتار زمانی همچنان قابل مشاهده است.

روی IR از role ir استفاده شود. نصب‌کننده یک‌طرف را خودکار restart نمی‌کند؛ هر دو طرف باید پیش از restart هماهنگ شوند. میانگین، انحراف معیار، سقف padding و jitter با متغیرهای محیطی مستند قابل تنظیم‌اند. تنظیم هر دو مقدار jitter روی صفر، تأخیر عمدی را خاموش می‌کند.

این فرمان هنوز نصب کامل یک‌خطی روی VM خالی نیست. تکمیل provisioning، enrollment اتمیک، حذف PSK، تست VM و تأیید عملکرد برای نسخه نهایی باقی مانده‌اند. فایل‌های کلید باید با دسترسی 0600 متعلق به کاربر سرویس باشند. حالت shaping جدید با R3 قدیمی سازگار نیست؛ اختلاف نسخه/فعال‌بودن در Noise handshake رد می‌شود.

## ج) تست ابطال

محیط اجرا: Linux amd64، Go 1.27.1 با checksum رسمی. نتایج محلی‌اند؛ اجرای CI یا پایلوت ایران ادعا نشده است.

| آزمون | نتیجه |
|---|---|
| تمام packageها، go test ./... | PASS |
| Race detector، go test -race ./... | PASS |
| go vet ./... | PASS |
| ۱۰۰۰ رکورد نرمال | SD=91.01 بایت؛ آنتروپی طول=8.131 بیت؛ ۳۴۵ طول متمایز |
| ۱۰۰۰ رکورد لاپلاس | SD=79.45 بایت؛ آنتروپی طول=7.929 بیت؛ ۳۱۳ طول متمایز |

| خودهمبستگی lag 1 تا 16 | بیشینه 0.095 و 0.068؛ زیر آستانه 0.2 |
| کنترل منفی طول ثابت، bucket، تناوب و sawtooth | همگی توسط معیار آماری رد شدند |

| HTTP/2 واقعی، کلید ناشناس، HTML و slow probe | PASS |
| Runtime دوطرف، هش و half-close، TWRL | PASS |
| گیرنده کند، backpressure و آزادسازی حافظه | PASS در mTLS و Noise |
| parser fuzz محدود، syntax نصب و build | PASS |

تست قدیمی گیرندهٔ کند در اجرای کامل شاخه مبنا نیز با timeout خاتمهٔ هدف شکست خورد؛ اجرای منفرد آن پاس می‌شد. علت fixture، انتظار FIN پشت بایت‌های TCP در حال تخلیه بود. fixture اکنون با لغو context، سوکت هدف آزمایشی را می‌بندد. شرط‌های backpressure، سقف حافظه و شروع مجدد پیشرفت حذف یا ضعیف نشده‌اند. طولانی‌مدت Stage-C soak همچنان گیت مستقلی است.

**ابطال ادعای «بدون افت سرعت»:** benchmark محلی برای رکورد ۱۶۴۰۰ بایتی، padding-only را حدود 4.93–5.16 میکروثانیه نشان داد؛ با jitter پیش‌فرض هزینه به حدود 1.06–1.10 میلی‌ثانیه رسید. timer در این محیط بیش از تأخیر درخواست‌شده می‌خوابد. بنابراین گیت حفظ سرعت باز است؛ نرخ حدود ۱۵ MB/s در این آزمون مصنوعی، سرعت اینترنت یا تونل واقعی نیست.

لاگ‌ها: [آزمون‌ها](r3.1-tests.log)، [race](r3.1-race.log)، [آمار](r3.1-statistics.log)، [ECRL](r3.1-ecrl.log)، [fuzz](r3.1-fuzz.log)، [benchmark](r3.1-codec-benchmark.log).

برای تأیید مقاومت فیلترینگ، trace واقعی HTTPS و BAFT، ارزیابی خارج از دادهٔ آموزش، طبقه‌بند با FPR ثابت و اندازه‌گیری goodput/latency لازم است. آنتروپی بالا اثبات تشخیص‌ناپذیری یا نبود همهٔ باگ‌ها نیست. این گزارش برای بررسی R3.1 آماده است؛ تأیید انتشار نهایی را پیش‌فرض نمی‌گیرد.
